# Architecture

How the Achieve Coaching site is put together, where to make common changes, and why things are the way they are. Read this first when you come back to the code after a break.

## What the site does

One landing page (`/`) that sells online coaching and collects applications. The order follows the client's brief: hero, every client result with the "In their words" reviews, the one-page application form, then who it is for. The form posts JSON to `/api/apply`, a Vercel serverless function that validates it and emails the coach through Resend.

```
Browser                                   Vercel
-------                                   ------
index.html (prerendered, static)
  ├─ ResultsGallery island  (photos + full-screen viewer)
  └─ ApplyForm island ── POST /api/apply (JSON) ──> src/pages/api/apply.ts
                                                     └─ handleApplicationRequest()
                                                          ├─ content type, size and JSON checks
                                                          ├─ applicationSchema (shared with the form)
                                                          ├─ spam checks (honeypot, fill time)
                                                          └─ ResendApplicationNotifier.send()
```

## Rendering model

- Sections are `.astro` files. They render to plain HTML at build time and ship no JavaScript.
- Anything a visitor interacts with is a React island (`.tsx`) loaded with `client:visible` and a `rootMargin`, so it hydrates just before it scrolls into view. There are two islands: `ResultsGallery` and `ApplyForm`.
- Small presentational components (`AchieveBtn`, `SectionTitle`, `QuoteCard`, `StepRow`) are React so both `.astro` sections and islands can use them. Used from `.astro` without a `client:` directive they also ship no JavaScript.
- Island props are serialised into the HTML, so they must be plain data: no functions, no class instances, no image imports.

## Images

- Photos are imported as modules (`import image3 from "@images/image-3.jpg"`), so a missing or renamed file fails the build instead of showing a broken image.
- `.astro` files turn them into responsive images at build time: `<Picture>` for the hero, `toResponsiveImage()` from `src/lib/images.ts` for gallery photos. That helper returns plain `{src, srcSet, sizes, width, height, alt}` data that can be passed to an island.
- Every image is offered as AVIF first and WebP second through `<picture>` (`ResponsivePicture.tsx`), so each browser picks the smallest format it supports.
- Gallery thumbnails carry a 16px blurred placeholder (a few hundred bytes, made with sharp at build time) shown as the image background until the real photo arrives.
- Islands never import image modules or `src/constants/resultPhotos.ts`. That file is server-only.
- Width lists live where they are used (`ResultsSection.astro`). Thumbnails stop at 720px wide; the full-screen viewer goes up to 1440px and only loads when opened, one photo either side of the current one.
- Sections far down the page use `deferRender` on `SectionContainer` (`content-visibility: auto`), so the browser skips laying them out until they are near the screen. Their placeholder heights are estimates, so `InPageJumps` (`src/lib/navigation/InPageJumps.ts`, started in `BaseLayout`) renders them for the moment of a `#section` jump; without it a header link could land hundreds of pixels past the section it names.
- The first build after changing image settings takes about two and a half minutes because AVIF encoding is slow. Astro caches the results in `node_modules/.astro`, so later builds take seconds.
- The hero image is the only image with `fetchpriority="high"` and `loading="eager"`. Everything else is lazy.

## Loading states

- `BrandLoader` (`src/components/common/BrandLoader.tsx`) is the one loading indicator: the white A in a blue-outlined circle with a ring of dots. `state="loading"` spins a bright arc of dots and glows; `state="idle"` is the grey, still version.
- Used for: the form while it sends, the photo viewer while Swiper or a photo loads, and in place of any photo that fails to load (grey logo over the blurred placeholder, so the card keeps its size).
- Styles live in `src/styles/effects.css` (`.brand-loader*`). With reduced motion the ring gently pulses instead of spinning.

## Full-screen photo viewer

- The strip on the page is plain CSS scroll snapping: the phone's own swipe, no JavaScript.
- Tapping a photo opens a native `<dialog>`. Inside it, Swiper (`LightboxSwiper.tsx`, with the Zoom, Keyboard and A11y modules) handles swiping, pinch and double-tap zoom and arrow keys. Swiper itself already arrived with the carousels, so opening the viewer only downloads its own 4 KB (gzipped) chunk plus the Zoom module.
- Escape, the back gesture, the close button and tapping the empty space around a photo all close it.

## The application form

**Client (`src/components/apply/`)**

- One page: name, WhatsApp number, email, then the optional Instagram or LinkedIn. Required fields come first. The client asked for no goal question and no steps, because most clients share the same goals.
- `react-hook-form` with `zodResolver(applicationSchema)`. `mode: "onTouched"` means a field is checked when you leave it, then re-checked as you type, so errors clear as soon as the input is fixed.
- Submitting focuses the first invalid field (`shouldFocusError`).
- Errors sit under each field, are linked with `aria-describedby` / `aria-errormessage`, and are announced politely. Their space is reserved so the layout does not jump.
- If the server rejects a field, the form shows the server's message under it and focuses it.
- The phone field uses `usePhoneInput` from react-international-phone for formatting, with our own `CountryPicker`. Typing digits matches dial codes by prefix (35 lists +350 to +359), letters match country names; arrow keys and Enter work. Flags come from `public/flags/`, not a CDN.

**Server (`src/lib/apply/handleApplication.ts`)**

1. Only `Content-Type: application/json` is accepted (415 otherwise). Browsers cannot send JSON cross-site without a CORS preflight, which this route never approves, so other websites cannot submit the form on a visitor's behalf.
2. Bodies over 8 KB are refused (413).
3. Broken JSON gets a 400.
4. `submissionSchema` validates every field with length limits and patterns and drops unknown keys (so a visitor on a cached older form that still sends `goal` is accepted). Errors return as `{error, fieldErrors}` with a 400.
5. Bots are quietly given a success response without an email being sent: a filled hidden `botcheck` field, or a form completed in under 2.5 seconds.
6. The email is built with every user value HTML-escaped, plus a plain-text version. Links are only built from parsed, validated handles.
7. Provider errors are logged on the server and the visitor gets a generic message (502). A missing API key gives a 503.

The handler receives its email sender as an `ApplicationNotifier` interface, so tests pass a fake one and nothing in `src/lib/apply/` knows about Resend except `notifier.ts`.

### Adding a field to the form

1. Add the rule to `applicationSchema` and its message to `VALIDATION_MESSAGES` (`src/lib/apply/schema.ts`).
2. Add a default in `DEFAULT_VALUES` (`useApplyForm.ts`).
3. Add its label and hint to `APPLY_FORM_COPY.fields` (`src/constants/applyForm.ts`).
4. Render a `TextField` (or a new field component) in `ApplyForm.tsx`.
5. Show it in the email (`buildRows` in `notificationEmail.ts`).
6. Add tests for the new rule and the email row, then run `npm run verify`.

## Design system

- Tokens are CSS variables in `src/styles/theme.css`, mapped to Tailwind utilities in `@theme inline`. Use `text-achieve-blue`, `bg-card`, `border-border-strong`, `text-muted-foreground` and so on; do not hard-code colours in components.
- One layout everywhere. The client wanted desktop to be the phone layout, so the site is a single centred column: the full screen on a phone, `--page-column` (37.5rem) wide on anything bigger, with the header and footer bars still spanning the screen. Sections use `SectionContainer`'s default `column` width.
- Scaling: `--col` is 1% of the column (`min(1vw, column / 100)`). Headings, gutters, section spacing, card padding, the header logo and carousel photo height are multiples of it, so a desktop shows the phone's proportions and line breaks about 1.5 times larger. Reading text grows less: the root font size eases from 16px on a 390px phone to 18px at full column width (written in `%`, so a reader's own text size setting still applies), which scales every `rem` by up to 12.5%.
- Fluid sizes: `text-display` (hero), `text-title` (section headings), `text-subtitle`, `text-lead`, `text-eyebrow`.
- Spacing: `px-gutter` for page side padding, `pt-section` / `pb-section` for section rhythm, `p-card` inside the big cards.
- Carousels: the photo strip and the reviews both use `SwipeCarousel` (`src/components/common/`), built on Swiper so they behave the same everywhere: swipe on touch, drag with a mouse, side-scroll on a trackpad (vertical wheel still scrolls the page), arrow keys once focused. Swiper is about 27 KB gzipped, shared by both carousels and the viewer; the islands hydrate as you scroll near them, so it stays off the hero's critical path.
- Swiper's stylesheet is imported in `global.css` into Tailwind's `base` layer so classes on slides (`w-auto`, `w-[85%]`) beat Swiper's defaults. Don't import `swiper/css` anywhere else: an unlayered copy would override those classes again.
- Swiper won't start a swipe on elements matching `noSwipingSelector`; its default includes `button`, which would make the photo strip (every photo is a button) unswipeable, so `SwipeCarousel` passes a list without it.
- Carousels run off the screen edge on a phone; on wider screens they fade out at the column edge instead (`.swipe-carousel` in `effects.css`).
- Headings use Montserrat 700/800 (`font-display`); body text uses the system Helvetica/Arial stack. Montserrat 800 is preloaded in `BaseLayout`.
- `SectionContainer` presets (`maxWidth`, `spacing`, `paddingTop`, `animationVariant`) control width and vertical rhythm. Add a preset there instead of padding a section by hand.
- `AchieveBtn` has `variant` (primary, outline, ghost), `size` (sm, md, lg), `fullWidth`, and `effect="shimmer"`. It renders a link when given `href` and a button otherwise.

## Progressive enhancement

Visual extras use modern CSS when the browser supports it and fall back to a plain, fully working page when it does not.

| Feature | Where | Without support |
| --- | --- | --- |
| Scroll-driven reveal (`.reveal-fade`, `.reveal-rise`) | `effects.css` | Content is simply visible. Also off for reduced motion. |
| Scroll progress line under the header | `effects.css` (`.scroll-progress`) | The line is hidden. Also off for reduced motion. |
| Deferred rendering (`.defer-render`) | `effects.css` | Sections render normally. |
| Header style change when stuck (`scroll-state` container query) | `effects.css` | Header keeps its translucent blurred style. |
| Native `<dialog>` for the photo viewer | `Lightbox.tsx` | Baseline in all current browsers. Tapping the dark space around a photo closes it on every browser, including Safari, which lacks `closedby`. |
| Scroll containment under the open viewer | `effects.css` | The page is still inert behind the dialog; it can just scroll a little on some browsers. |
| Shimmer and shine effects | `components/effects/` | Static button and border under `prefers-reduced-motion`. |
| Current-section lamp in the header (`scroll-target-group`, `:target-current`) | `effects.css`, `SectionSpy.ts` | Chrome and Edge track sections natively; elsewhere `SectionSpy` uses an `IntersectionObserver` and adds the `target-current` class. Both paths set `aria-current`. A hidden `#top` link in each nav keeps the lamp off while the hero is showing. |
| Logo shine sweep and header button border beam | `effects.css` (`.brand-logo__shine`, `.border-beam`) | Each runs once (the beam three laps) after load, then rests. Off for reduced motion. |

## Decisions and gotchas

- **No third-party HTML minifier.** `astro-compress` runs with `HTML: false`. Its minifier moved whitespace around the `<!-- -->` markers React puts between text nodes, which broke hydration of the form (React error 418). Astro already compresses its own HTML.
- **Swiper is pre-bundled in dev** (`optimizeDeps.include` in `astro.config.mjs`). When it was only reached through the viewer's lazy import, Vite found it late and the open page asked for a stale copy (504, viewer would not open). The carousels import it directly now, but pre-bundling keeps the Zoom module and the viewer safe. Production builds were never affected. Astro 7 runs `astro dev` in the background: restart it with `npx astro dev stop` first.
- **No `vite.esbuild` options.** Astro 7 uses Vite 8, which ignores them (it uses Oxc). Server `console.error` calls are kept on purpose so failures show in Vercel logs.
- **Flags are self-hosted** in `public/flags/` (218 SVGs from country-flag-icons, MIT). The phone library's default flags came from a third-party CDN.
- **Search previews.** `BaseLayout.astro` sets the title, description, canonical URL, Open Graph image, a square favicon set, a web manifest and `WebSite` / `Organization` structured data. Google picks these up only after the production site is recrawled.
- **Images are not re-encoded in the repository.** The originals in `src/assets/images/` are large (one is 19.7 MB) but only resized copies are sent to visitors. Replacing the originals with 2400px versions would make builds and clones faster.
- **Vitest uses Astro's Vite config** (`vitest.config.ts` with `getViteConfig`) so path aliases like `@/` work in tests. Code that imports `astro:assets` or `astro:env` cannot be unit-tested directly, which is why the API route is a thin wrapper around `handleApplicationRequest`.
